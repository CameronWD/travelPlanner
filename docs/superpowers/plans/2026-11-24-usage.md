# Usage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Goal:** Record which screens and named actions each signed-in Traveller uses (spec §1), never anything else (§2). Records go up from the browser in batches (§3), recording can be switched off from Admin and records go after 180 days (§4), and Admins read them as counts on the Admin screen and through `npm run usage:report` (§5). `/privacy` says so (§6). This ships to production on Fri 27 Nov, four days before a five-week freeze, so every choice below is the boring one this codebase already uses.

**Architecture:** One table of closed-list values (`UsageRecord`) and a single-row switch (`UsageSwitch`), in one migration whose CHECK constraints make free text impossible in the database itself. One shared, zod-free module of closed lists (`lib/usage/lists.ts`) is the only vocabulary on either side. One authenticated JSON endpoint (`POST /api/usage`), modelled on `app/api/client-error/route.ts`, takes batches, re-validates every record, takes the Traveller from the session, drops Trips the Traveller is not on, and strips day offsets on the server for a Traveller with a Surprise hidden from them. A client module (`lib/usage/client.ts`), modelled on `lib/feedback/queue.ts` and `lib/offline-status.ts`, queues records in localStorage (capped at 500) and flushes them with `fetch(..., { keepalive: true })`. Three render-nothing components mount it: one in the `(app)` layout, one in the `(focus)` layout, one in the trip layout. Each named action is one added call in an existing handler. Nothing rendered on the server changes: every component renders `null` and every client-wrapped link renders the same markup. **Task 0 (three serial commits) comes first; then five lanes (A to E), which share no file, run in parallel in one checkout.**

**Tech Stack:** Next.js 16.4 (read `node_modules/next/dist/docs/` before using any Next API), React 19 with the React Compiler, Prisma 7 on Postgres (Neon in production), Tailwind v4, Vitest. No new dependency.

**Spec:** `docs/specs/2026-11-24-usage.md`. Decision: ADR 0078 (`docs/adr/0078-usage-is-recorded-first-party-as-counts-of-screens-and-named-actions.md`). Language: `CONTEXT.md` **Usage** (line 301, already at HEAD), **Activity**, **Admin** (line 385), **Surprise**, **Phase** (line 33). Saved copy: ADR 0077. Carousel: ADR 0065. Loading: ADR 0063 (one `loading.tsx`).

## Data model (Task 0.1)

`prisma/schema.prisma`, after `GoogleUsage` (:1578). No relations, like `AiUsage` (:1466-1469: "a row outlives its Trip"), so deleting a Trip or an account never has to find these rows (spec §4). No Prisma `enum`: the file's header (:4-8) keeps enum-ish values as `String`, and the database holds them to the lists through CHECK constraints.

```prisma
model UsageRecord {
  id         String   @id @default(cuid())
  screen     String?
  action     String?
  detail     String?
  userId     String
  tripId     String?
  phase      String?
  mode       String
  appearMs   Int?
  savedCopy  Boolean  @default(false)
  dayOffset  Int?
  occurredAt DateTime
  receivedAt DateTime @default(now())

  @@index([tripId, occurredAt])
  @@index([occurredAt])
  @@index([receivedAt])
}

model UsageSwitch {
  id          String   @id @default("usage")
  recording   Boolean  @default(true)
  updatedById String?
  updatedAt   DateTime @updatedAt
}
```

- `(tripId, occurredAt)` serves the Admin's per-Trip read; `occurredAt` serves the 180-day delete; `receivedAt` serves "when the last one arrived". `count(*)` serves the total.
- `occurredAt` is when it happened on the device (records wait offline); `receivedAt` is the server's clock.
- `UsageSwitch` copies `CronHeartbeat` (:1400-1408, `id @default("digest")`): one row, and **no row means on**, so nothing needs seeding and the default holds on a fresh database.
- No column takes free text. The only strings that are not closed-list values are `userId` (from the session) and `tripId` (accepted only when it is a Trip the Traveller is on).

## Endpoint contract (Task 0.2)

`POST /api/usage`, `app/api/usage/route.ts`. Request `Content-Type: application/json`, same origin, cookies sent by default.

Body: `{ "records": UsageWireRecord[] }`, no other top-level key, 1 to `MAX_BATCH_RECORDS` records. A record is exactly one of:

```ts
type ScreenWire = { screen: UsageScreen; at: number; mode: OpenMode; tripId?: string; phase?: UsagePhase; ms?: number; saved?: boolean; dayOffset?: number };
type ActionWire = { action: UsageAction; at: number; mode: OpenMode; detail?: UsageDetail; tripId?: string; phase?: UsagePhase; dayOffset?: number };
```

| Case | Response | Stored |
|---|---|---|
| No session (`auth()` returns null) | `401`, empty body | nothing; the body is never read |
| Over 30 requests a minute for this user (`createRateLimiter`, keyed by user id) | `429` | nothing |
| `content-length` or the read text over `MAX_BODY_BYTES` | `413` | nothing |
| Not JSON; not `{ records: [...] }`; an extra top-level key; 0 or over 100 records | `400` | nothing |
| Recording off (`UsageSwitch`) | `200 {"recording":false}` | nothing |
| Otherwise | `200 {"recording":true}` | every record that passes, as below |
| The database write throws | `503`; `reportError(new Error("Usage batch was not stored"), { route: "/api/usage", source: "server", userId })` with a fixed message, never the original error (the `lib/ai-usage.ts:31-36` rule) | nothing |

Every response carries `Cache-Control: no-store`. Within a well-formed batch, a record is **dropped on its own** (the rest are kept, the `lib/feedback/queue.ts:96-104` lesson) when: it has any key outside its shape (so an added `name` or `userId` drops the whole record, never just the field); it has both or neither of `screen`/`action`; `screen`, `action`, `detail`, `phase` or `mode` is not in its list; `detail` does not match `ACTION_DETAILS[action]` (required where that list exists, absent elsewhere); `at` is not an integer in `[now − 180 days, now + 5 min]`; `ms` is not an integer in `[0, 120000]` or appears on an action; `saved` is not a boolean or appears on an action; `dayOffset` is not an integer in `[−1000, 1000]` or appears anywhere but screen `day` and action `day-changed`; a trip screen has no `tripId`, an app screen or `share-link-opened` has one; `tripId` is not a string of 1 to 64 characters (no pattern: membership is the guard, and a Trip id made by a seed script need not look like a cuid); `phase` is present without `tripId` or missing with it; its `tripId` is not a Trip this user is a member of, or that Trip has `deletedAt` set; it names a sixth distinct Trip in one batch.

The Traveller is always `session.user.id`, never from the request. For a Trip where the Traveller has a Surprise hidden from them (`loadSurpriseVisibility(tripId, userId)` → `hiddenRootIds.length > 0`, `lib/surprise-visibility.ts:120-163`), every record's `dayOffset` is set to null before it is stored; the method of a `day-changed` stays (spec §2). Visibility is loaded only for Trips whose records carry a `dayOffset`.

**Why `fetch` with `keepalive`, not `sendBeacon`.** A beacon returns no response, so the browser could never learn the switch is off, nor tell a refused batch (drop it) from a failed one (keep it). `fetch(url, { method: "POST", keepalive: true })` outlives the page like a beacon, gives a response while the page is alive, and uses one code path for every flush. Both share the same in-flight body limit of 64 KiB per page; a batch is at most 100 records of about 200 bytes, under `MAX_BODY_BYTES` (32 KB), so a hide flush always fits. iOS Safari has supported `keepalive` since 13.

### Task 0.3: the browser queue

**Files:** new `lib/usage/client.ts`, new `lib/usage/client.test.ts` (line 1 `// @vitest-environment jsdom`: a `.ts` test runs in node unless it opts in, per the vitest config's projects).

Module state, no React, like `lib/feedback/trip-store.ts`.

Storage: `localStorage` key `teepee.usage.v1`, value `{ "u": userId, "r": UsageWireRecord[] }`. localStorage over IndexedDB because the queue is at most 500 records of about 200 bytes (100 KB), it is read and written synchronously after paint, and the app already relies on it the same way. Every read and write is in try/catch: in private mode, with storage blocked, or on a quota error, the queue falls back to a module-level in-memory array, capped the same way, and nothing throws.

Exports (each wraps its whole body in try/catch):

- `startUsage(userId: string): void`. Idempotent per document: the first call installs the listeners and the timer; later calls only update the user. If the stored `u` is another user, the stored queue is cleared first (a previous account's records never go up under this session). It always writes `{ u: userId, r: [...] }`, even with an empty queue, so the share page's check (`sendUsageOnce`) sees a signed-in browser after every record has been sent. Records enqueued before the first call wait in memory and join the queue at start.

Flushing (all inside the module):

- **Triggers.** A 30 s interval that runs only while `document.visibilityState === "visible"` (started on `visible`, cleared on `hidden`), so a background tab sends nothing and never keeps Neon awake; `visibilitychange` to hidden; `pagehide`; `online`. No flush at start: the first tick comes 30 s after the page drew.
- **Guards.** Nothing is sent when the queue is empty, when `navigator.onLine === false`, while a send is in flight (one per tab), while backing off, or after the document stopped (below). The hide and pagehide flushes respect the same guards.
- **Send.** The oldest `MAX_BATCH_RECORDS` records, `fetch("/api/usage", { method: "POST", headers: { "content-type": "application/json" }, body, keepalive: true, signal })`, with `signal` from `AbortSignal.timeout(15_000)` where that exists. Records leave the queue only after a 2xx: on success, remove the sent records from the **current** stored queue by value (first match of each `JSON.stringify`), so records another tab added meanwhile stay. A page killed after its hide flush landed but before it removed them sends them again next time: a rare duplicate, accepted (Decisions).
- **Outcomes.** 2xx: sent, backoff reset; if the body says `recording:false`, clear the queue and stop for this document. 400 or 413: drop that batch (it can never succeed). 401: clear the queue and stop for this document (the session is gone; its records must not go up under the next one). 429, 5xx, a network error or a timeout: keep, and back off 30 s, 60 s, 120 s, 240 s, then 300 s at most, until a 2xx.
- **Stopped.** While stopped, records are not enqueued. The next document starts again (the first flush asks the server).
- **Cap.** Every write keeps the newest `MAX_QUEUE` (500) records and drops the oldest.

## Review Focus

The five ways this could hurt the owner on the trip, and what must hold:

1. **A retry storm on one bar of signal.** At most one request in flight per tab; nothing when the queue is empty, when `navigator.onLine` is false, or while the page is hidden; after a failure the wait doubles from 30 s to a 5-minute ceiling and only a 2xx resets it; the `online` event and the hide flush respect the wait; a send gives up after 15 s. A 4xx is never retried.
2. **The queue growing without bound.** 500 records at most, in localStorage and in the memory fallback alike, oldest dropped on every write; a record is about 200 bytes, so the queue stays near 100 KB; a 401 or "recording off" empties it.
3. **A slow endpoint holding a connection on Neon.** The handler does `auth()`, at most one switch read every 30 s per instance, one membership query, a Surprise read only for Trips whose records carry a day offset (at most five Trips per batch), and one `createMany`. No transaction, no retry on the server, no waiting on anything else. A failure answers 503 at once. No browser waits on the response for anything a Traveller sees.
4. **An unhandled rejection or a throw on every page.** Every exported client function is wrapped; every promise is caught; no module touches browser globals at import; every recorder component renders `null` and does its work in effects; a call site's added line runs before the handler's own logic and cannot throw. Task 0.3's tests prove it with `fetch`, `matchMedia` and `localStorage` broken.
5. **The switch not actually stopping writes.** The server reads the switch on every batch (at most 30 s stale per instance) and stores nothing when it is off, whatever the browser sends; the browser empties its queue and stops for that document on `recording:false`. The integration test proves no row is written while off.

Privacy, read with the five: the server, not the browser, strips day offsets for a surprised Traveller; a record with any unexpected key is dropped whole; the share page's record carries no Trip; the property test proves no stored string can be anything but a listed name, the session's user id or a member Trip's id.

## Questions for the orchestrator

1. **Google Maps cost per Trip cannot be built from what TEEPEE keeps.** `GoogleUsage` is `(day, sku, count)` with no Trip and no price (`prisma/schema.prisma:1576-1584`, `lib/google-usage.ts:5-17`); `lib/google-budget.ts` holds free monthly allowances, not prices; maps drawn in the browser are not counted anywhere. D1 shows the AI cost per Trip (from `AiUsage.tripId`) and, for Google, the app-wide server call counts over the Trip's dates, labelled "on every Trip", with no money figure. Say if Google should be left out instead.
2. **Which Trips can the Admin pick?** CONTEXT.md **Admin** says Admin standing "grants nothing on Trips the Admin isn't a Traveller of". D2 lists and reads only Trips the Admin is on; `usage:report` (an operator script) reads any Trip. Say if Admin should see every Trip.
3. **Phase has five values in the code.** The spec lists four; `TripPhase` (`lib/trip-phase.ts:13-18`) adds `final-prep`. The table stores all five. Say if `final-prep` should be stored as `planning`.
4. **The Surprise rule's second reason.** As written, only the surprised Traveller's day offsets are stripped. The spec's reason also says the offsets could "give the planner's interest away to the surprised": if the surprised Traveller is an Admin, the planner's offsets on the surprise days are readable. The safer rule is to strip day offsets for everyone on a Trip with any live Surprise. Built as written unless you say otherwise.
5. **Turning recording back on.** Off stops a browser for the rest of that document (a PWA left open keeps it until it is reloaded or relaunched); a new document asks again with its first batch. Off takes effect within a minute; on takes effect at each device's next load. Polling while off would mean requests while off, which the spec forbids.
6. **Screens off the list.** What's new, a Trip's `/more`, `/compare` and `/today` pages are not recorded (not on spec §1's list). Say if any should be.
7. **Beta and main share one table.** Records carry no site, so a beta tester's Usage lands beside main's. The server could stamp the site itself (as Feedback does, `lib/feedback/site.ts`) with one more closed-list column. Not built.
8. **Where should the decisions below be logged?** The spec has no decisions section; the previous wave used `docs/audits/…-decisions.md`.

## Decisions to log (orchestrator)

| Id | Built as | The other way |
|---|---|---|
| U1 | Two tables in the one migration: `UsageRecord` and a one-row `UsageSwitch` (no row means on). | A key-value settings table, or the `OperatorNotice` ledger. |
| U2 | The database CHECKs every name against the lists; adding a name needs a migration. | App-side validation only, as other enum-ish columns here. |
| U3 | A record with any unexpected key is dropped whole; bad records drop one by one, never the batch. | Strip unknown keys and keep the rest. |
| U4 | `fetch` with `keepalive` for every send. | `sendBeacon` on hide. |
| U5 | At least once: a record leaves the queue only after a 2xx; a page killed between its hide flush landing and its removal sends it twice. | At most once: take before sending and lose a batch that fails while the page is frozen. |
| U6 | Off empties the browser's queue and stops it for that document; 401 does the same. | Keep queueing while off; poll for on. |
| U7 | Time to appear: navigation start (or the tap) to the first paint after the screen's recorder ran; null for Back/Forward; the Trips list counts its skeleton. | First contentful paint only; Largest Contentful Paint. |
| U8 | A browser reload records the screen again; a re-render, a refresh in place or a day change does not. | Skip reloads. |
| U9 | Saved copy is true for any first screen the worker answered from its cache, including ADR 0077's 4-second timeout on a slow network, not only with no connection. | Only when `navigator.onLine` is false. |
| U10 | Phone means a coarse pointer (an iPad counts as a phone); phone app means coarse and standalone; an installed app on a computer is "desktop". | User-agent sniffing. |
