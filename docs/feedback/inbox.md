- **Claude connection · Christmas in Europe 2026 · Cam · 2026-10-13** — `cmv7bza6t000506l3x5tx34f0`
  Bug: wrong timezone for the "home" end of a Transport leg.
  
  When one end of a leg is Home (from.home or to.home = true), the local time is shown in the timezone of the stop at the OTHER end of the leg instead of the home timezone. The stored UTC times are correct; only the local conversion is wrong.
  
  Examples on "Christmas in Europe 2026" (home base: Gold Coast, which is UTC+10 and has no DST):
  1. Gold Coast (OOL) → Denpasar (DPS): depAt 2026-12-04T07:50Z is shown as 15:50 "GMT+8" (Bali time). It should be 17:50 Gold Coast time.
  2. Rome (FCO) → Brisbane (BNE): arrAt 2027-01-08T07:30Z is shown as 08:30 "GMT+1" (Rome time). It should be 17:30 Brisbane time.
  
  Seen in get_trip_plan output over MCP (departs/arrives.localTime and zone). Not yet checked whether the in-app UI or the edit form has the same problem. If the edit form uses the same fallback, a typed home-end time would be saved with the wrong UTC.
  
  Suggested fix: store a home timezone as an IANA zone (e.g. Australia/Brisbane) on the trip or traveller, geocoded from homeBase like stops are, and use it whenever an endpoint is Home. Using an IANA zone rather than a fixed GMT offset also handles DST.
  
  Related (MCP): update_transport won't accept fromStopId together with depPlace ("Give fromStopId or depPlace, not both"). But existing legs (e.g. Paris → London) do have both a stop and a station name, so there's no way over MCP to add a station name to a leg without detaching it from its stop.

- **Claude connection · Christmas in Europe 2026 · Cam · 2026-10-13** — `cmv7c1dfw000606l3cv8t0fji`
  MCP: allow a station or place name on Transport legs that are linked to Stops
  
  Problem: update_transport rejects fromStopId + depPlace (and toStopId + arrPlace) together with "Give fromStopId or depPlace for departure, not both." Passing only depPlace detaches the leg from its Stop. So over MCP there's no way to say WHERE in a city a leg leaves from without breaking the link to the plan.
  
  The data model already supports both: Paris → London has from.stopId = Paris AND depPlace = "Paris Gare du Nord", and London → Aghalee has stop links plus "London Heathrow (LHR)" / "Belfast City (BHD)". So the restriction seems to be only in the API validation, not in the model.
  
  Why it matters: the Stop is the city you're staying in, but the station is where you actually need to be. Cities often have several possible departure points (main rail station vs central bus station vs airport), and bus legs especially leave from somewhere other than the main station. The exact place is what you need for directions, timing, and the evening-before Digest. On this trip I had to put stations in the notes for 4 legs (Strasbourg → Frankfurt, Frankfurt → Paris, Belfast → Dublin, Milan → Rome) as a workaround.
  
  Suggested change: treat depPlace/arrPlace as an optional detail on top of a Stop link:
  - stopId only → leg linked to the Stop, no specific place (current behaviour)
  - place only → leg not linked to a Stop (e.g. Malpensa → Como transfer)
  - stopId + place → linked to the Stop, with the precise station/terminal as a label
  Also worth doing: make add_transport behave the same way, and optionally geocode the place so it can show on the map or link to directions.
